## Identity and delivery rules

- Guaranteed reward identity is `reward:<reward_id>:<quantity_index>` and is derived only from the authored reward ID and quantity position.
- Guaranteed modifiers are generated from `LootGenerator.seed_for(instance_id)` and `generate_guaranteed()`. They do not consume or depend on ordinary monster occurrence RNG.
- The item level is copied from the resolved authored reward definition. Node filename/order/suffix is not used by the live reward path.
- A successful terminal commit creates one entitlement per authored `first_clear` reward. Existing entitlement IDs make completion/retry/replay a no-op for that reward.
- If inventory has capacity, claims move pending items into `item_instances` and append the item ID to that entitlement's `delivered_item_ids`. If full, generated items remain in `pending_rewards` and are saved.
- Claims are item-by-item and stop at the first unavailable capacity. Repeating a claim or reloading cannot duplicate an instance because `add_campaign_instance()` rejects an existing instance ID.
- Discarded campaign reward IDs are persisted. Reconciliation skips a discarded reward, preserving the decision instead of regranting it.
- Legacy completion reconciliation uses completion evidence plus an existing `legacy:<base_id>` instance or a one-time transitional legacy insertion. It records a delivered entitlement and does not regrant on subsequent loads. Capacity failure leaves the reward unreconciled for a later retry. Existing discarded history remains authoritative when available.
